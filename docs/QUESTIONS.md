## 2026-10-11 · WP-16 · AGENT — Security finding: parser differential in `packages/extractor/src/parse/amount.ts` (FIXED)
- **Finding (from ORCH/security review):** my first amount parser NFKC-folded its input, stripped any 2-6 letter "currency token" anywhere in the string, and accepted narrow NBSP / typographic apostrophes / leading zeros. Examples that parsed to a number while a stricter reader would not: `1USD000` -> 1000 (token replaced by a grouping space), full-width `１０００`, `1<U+2019>000`. A parse that differs from K-02's is a money bug even though the kernel re-checks (K-02 step 5), because the extractor's `parsedBaseUnits` is what the human-facing flow and consensus see.
- **Fix (commit "fix(extractor): amount parser refuses anything K-02 could read differently"):** `parseAmountPrinted` now (1) runs `normalizeUntrusted()` first and refuses (`HIDDEN_CHARS`) if it would remove anything; (2) does no NFKC folding: any non-ASCII digit, full-width form, unicode minus is refused; (3) accepts only the K-02 grouping set (space, NBSP, U+2009, ASCII apostrophe); (4) accepts one currency code/symbol only as a prefix or suffix of the whole string, never in the middle; (5) refuses leading zeros, any sign/bracket, exponent forms, bad group sizes, too many decimals; (6) the raw `printed` string is never rewritten (validator checks it is a substring of the normalized document), so K-02 re-parses the same bytes. Contract: wherever the extractor and K-02 could differ it returns `invalid`/`ambiguous`, never a different number.
- **Tests:** `test/amount-differential.test.ts` (38-row table, a K-02 reference transcription compared on 20k generated strings: accept => identical value, ambiguous => K-02 ambiguous; accepted values round-trip through `formatBaseUnits`; a negative control showing a kernel-style folding reader would accept inputs we refuse).

## 2026-10-11 · WP-16 · AGENT — Security finding: budget-cap bypass in `packages/extractor/src/llm/budget.ts` (FIXED)
- **Finding (from ORCH/security review):** the first wrapper reserved an ESTIMATE (input tokens guessed as chars/3, which can under-count) and only the estimate was checked, so a call whose real cost overshot could pass, parallel calls could each see room (depending on the ledger), and a failed/timed-out provider call left the reservation at the estimate.
- **Fix:** (1) `BudgetedLlm.call` reserves the MAXIMUM possible cost before the provider call: input bound = UTF-8 bytes of everything sent (a token is never shorter than a byte), output bound = `maxOutputTokens`, priced by the operator's `CostModel`; the ledger contract is "check and book atomically against remaining per-principal AND global budget" (`InMemoryBudgetLedger` does it in one synchronous step; the Postgres ledger must use one conditional UPDATE). (2) Every attempt counts: a failed/timed-out call is settled at the full reserved maximum; an invalid usage report (NaN/negative/fractional) is also charged at the maximum; a retry is a new `call()` and so a new reservation. (3) Integer money only: bigint micro-USD, `CostModel` rejects negative/non-bigint prices and non-integer/negative token counts, invalid `maxOutputTokens` is refused (`INVALID_COST`); unknown model => `UNPRICED_MODEL`; a missing/malformed ledger or empty principal refuses to construct. (4) Both caps are enforced; the window ("day") is read from the ledger's own server clock and no request field can move it (the per-principal key is a caller-supplied hash, so the global cap is the backstop against principal rotation; the service must derive it server-side, salted, from IP/session).
- **Tests:** `test/budget.test.ts` (19): concurrent calls where only those that fit run, max cost > remaining refused although the actual cost would fit, settlement releases headroom, per-principal cap, window not caller-controlled, retry accounting (failed attempts charged at max; retry loop cannot outrun the cap), invalid usage charged at max, unknown price / invalid tokens / missing ledger refuse, and a NEGATIVE CONTROL (a check-then-spend ledger overspends, proving the concurrency test is sensitive).
- **For KERNEL-SVC/WEB:** implement `BudgetLedger.reserve` atomically (single conditional UPDATE/INSERT ... WHERE spent + max <= cap, for the global row and the principal row in one transaction). Reservation granularity is conservative (4x over-reservation is normal for English text); size caps accordingly. **Status:** FIXED, awaiting ORCH re-review.

## 2026-10-11 · WP-16 · AGENT — Security findings in the extractor validation layer: signal suppression, currency confusion, unanchored substring, token.ts (FIXED)
- **F1 fail-open / signal suppression.** Before: a validation failure returned only the failure, dropping the injection/hidden-character signals; the sink and context errors were swallowed. Now: `signals.ts` computes document signals (HIDDEN_CHARS, injection phrases, address-change language) from the normalized text BEFORE any model runs; every `ExtractionFailure` carries `signals` and a typed `disposition` (`ESCALATE` when any signal exists or signals are unavailable e.g. oversize, otherwise `HOLD`; there is no "proceed"); signal anomalies are merged first so a model flooding 50 junk anomalies cannot push them out of the cap; a scanner crash becomes `scanError` (a risk flag), a validator exception becomes a typed `INTERNAL_ERROR`; sink / context / ledger-write problems are returned as `warnings`.
- **F2 currency confusion.** Before: case-insensitive `includes`, `$` treated as USDC, `USD` found inside `USDC`. - **token.ts (two findings).** (1) `toLowerCase()` shifted indexes ("İ" is 2 code units; Kelvin sign folds to "k"): folding is now ASCII-only and length-preserving, and the invariant is asserted.
