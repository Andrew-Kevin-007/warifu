## 2026-10-11 00:50 IST · WP-01 · SCHEMAS — Interpretations fixed in schemas v0 (review before the G1 freeze)
`docs/05` says "if code and doc disagree, fix the doc in the same PR", but `docs/` belongs to DOCS, so they are listed here instead. Each one is a reversible v0 choice; changing one after G1 is an RFC (`schemas-v1.1`).
1. **ISODateTime = whole-second UTC** `YYYY-MM-DDTHH:MM:SSZ` (`05` §1 says only "RFC 3339 UTC, 'Z'"). Reason: one spelling per instant inside hashes; contracts are second-granular. `Date#toISOString()` (`.000Z`) does not parse; use `isoFromEpochSeconds`.
2. **Text hashes** `Receipt.humanExplanationHash` and `Document.normalizedHash` = keccak256 of the text's UTF-8 bytes, not keccak256(JCS(string)). The docs say only "hash". **WP-02 to confirm.**
3. **termsHash preimage** uses the key `cap` (the `05` field list) carrying `capBaseUnits`; milestones enter without their mutable `status`.
4. **Engagement `ownerSig`/`payeeSig` are nullable** (null until signed; the `05` §3 columns are nullable). `05` §2 shows `Hex`.
5. **ConsensusDiff `a`/`b`** hold the JCS text of each value, so `null` and the string `"null"` differ.
6. **ReplayBundle.receipts are `SignedReceipt`** (receipt, hash, signature, signer) so `verify-bundle` can check signatures (`15` §7). `05` shows `Receipt[]`. `certificate` is nullable.
7. **Shapes the docs name but do not spell out**, defined by SCHEMAS: `EvidenceFixture` (`15` §2) and `TimingProposal` (`05` §2 → `03`, which has no definition).
8. **normalizeUntrusted removes more than the guardrail-7 list:** also U+061C, U+2060–U+2064, U+00AD, U+034F, U+180E, tag characters U+E0000–U+E007F, and lone surrogates (counted as `invalid`). It returns per-category `counts` next to `{normalized, removedCount}`.
9. **RESOLVED (ORCH, 2026-10-11 01:06 IST): milestoneId collisions → keep the uuid rule.** `05` §1 derives `milestoneId = keccak256(JCS({tenantId, slug|uuid}))`, but slugs are unique only per engagement, so two engagements of one tenant with a "design" milestone would get the same id. **Rule:** milestone ids are derived from a `uuid` with `deriveMilestoneId({tenantId, uuid})`, which rejects a slug at compile time and at runtime; the preimage stays as `05` §1 has it (no `engagementId` added). Engagements may keep using a slug. KERNEL-CORE (K-05/K-06) and CONTRACTS take milestone ids as given.

## 2026-10-13 · WP-05 kernel fixes after the re-baseline · KERNEL-CORE → KERNEL-SVC/ATTACK/ORCH — decisions (findings 1-5 of "WP-23 re-baseline")
Branch `wp-05/kernel-fixes-rebaseline`. Where the spec was ambiguous the stricter, fail-closed reading was taken and is stated below. Numbers live in the generated `results/*.md` (SIMULATED).

**Finding 1: sandbox evidence mismatch (DONE).**
1. **Which side is right: kernel-core's.** docs/04 K-09 (sandbox) says evidence exists only if the fixture store holds a record for the EXACT spec entry. Only an evidence record that carries the entry it satisfies lets the pure kernel verify that binding itself, so the contract in `kernel-core/src/evidence.ts` (`payload.requirement` JCS-equal to the signed entry) stays, and the service now emits it: `fixtureToCollected` payload is `{requirement, requirementHash, fixtureId, fixture}`. A record minted for a different entry, the old `{requirementHash, fixtureId, fixture}` shape, and a store denial row are all DENIED by the kernel (tests).
2. **The production shapes disagreed too (same root cause, found by comparing every type).** The service sent `owner:eip712:MilestoneAck` (kernel: `eip712:MilestoneAck`) with no `milestoneId` in the payload; `url:<finalUrl>` as the URL_HEALTH source with no `url` in the payload (kernel: source = the signed spec url, payload.url = the spec url); `kernel:artifact-upload` (kernel: `kernel:artifact`). So production OWNER_ACK, URL_HEALTH and ARTIFACT_HASH evidence was DENIED as well. Fixed on the service side; CI_PASS already agreed. The source strings are now exported from kernel-core (`productionEvidenceSource`, `urlEvidenceSource`, `SOURCE_*`) and imported by the collectors, so they cannot drift again. A signed URL longer than the 512-char `Evidence.source` field is identified by `url:sha256:<hashJcs(url)>` on both sides (the service already had that fallback; K-09 now accepts exactly it).
3. **Unreachable site is MISSING, not DENIED.** A collector error (`failure()`) used to be reported from source `denied:egress`, so a site that is down read as `EVIDENCE_SOURCE_DENIED`. It now reports from the requirement's own source and K-09 reads it as MISSING. Real refusals (`denial()`) keep `denied:egress`.
4. **Hash mismatch is the spec'd REJECT (stricter reading).** docs/04 K-09: "evidenceTampered (hash mismatch) => REJECT EVIDENCE_HASH_MISMATCH". The collectors record a mismatch as `result: FAIL`, and K-09 mapped any FAIL to FAILED (HOLD), so that REJECT was unreachable with real collector output. For URL content hash and artifact hash the payload's facts now decide (`factState`): ERROR => MISSING; status wrong => FAILED; pinned/signed hash differs => TAMPERED (REJECT) whatever the collector's PASS/FAIL; facts fine but result FAIL => FAILED. Consequence for the product: a payee who uploads the wrong file gets a REJECT on that intent (never retried) and must re-invoice under a new number; an owner OWNER_ACK override cannot satisfy a TAMPERED requirement. If ORCH prefers the friendlier HOLD, change `factState` and the three tests that name it; the safe side (nothing is paid) is the same.
5. **Tests**: `kernel-core/test/checks-k09.test.ts` (collector-shaped FAIL/ERROR cases, long-url source, source constants); `services/kernel/test/evidence/kernel-contract.test.ts` (real collectors and fixtures through the real `assessEvidence`, per type and per profile, no DB) and `kernel-contract.local.test.ts` (real Postgres and the real routes: rows loaded by the context assembler's own `loadEvidence`, then `assessEvidence`; sandbox all-SATISFIED, missing fixture DENIED, production CI+URL+artifact+signed ack SATISFIED, wrong artifact TAMPERED, red CI FAILED, down site MISSING).

**Finding 2: K-04 and partial instalments (DONE).**
1. **Reading chosen.** docs/04 K-04 says a second RELEASE on the same (engagement, milestone) is `REJECT MILESTONE_ALREADY_PAID`; K-05/K-08 allow `partialAllowed` milestones and K-08 already caps the cumulative partial releases at the milestone amount (OVERPAY). Read together, "already paid" for a `partialAllowed` milestone (read from the SIGNED milestone terms) means the earlier RELEASEs cover the whole milestone amount. K-04 now rejects only then (sum of earlier RELEASE gross amounts >= the milestone amount; an earlier release with an unknown amount counts as the whole milestone, as in K-08). A milestone that does not allow partial payment, or whose signed terms are unavailable, keeps the strict reading (any earlier RELEASE rejects). Whether the NEW instalment still fits is K-08's job and unchanged (`prior + gross > milestone amount` => REJECT OVERPAY).
2. **Still stops, by design:** exact intentId replays (REPLAY), the same document under another intent (ESCALATE DUPLICATE_DOC), and an equal-amount instalment for the same payee under another invoice number within 7 days (ESCALATE NEAR_DUPLICATE: two honest equal instalments of one milestone therefore cost one owner click; the spec's rule has no "different instalment" exception and an equal-amount re-invoice is exactly what it exists to catch).
3. **Binding on KERNEL-SVC/RECONCILER (WP-14/15):** a `partialAllowed` milestone must stay PENDING/EVIDENCE_OK until its releases cover the amount; if a service marks it `PAID` after the first instalment, K-05 (milestone status) rejects the next one.
